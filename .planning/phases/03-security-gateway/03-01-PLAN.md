2. **Opening section — "Understanding the Secure Dataplane"** (2-3 paragraphs):
   - Frame for network architects: "loxilb-enterprise encrypts and protects traffic at three distinct layers — each optimized for different deployment patterns and security requirements."
   - Explain the layered model: IPsec operates at L3 (node-to-node tunnel encryption), mTLS at L7 (service-to-service mutual authentication), eBPF at kernel datapath level (DDoS protection, IP filtering before packets reach userspace).

3. **Three-Layer Comparison Table**:

| Aspect | IPsec | mTLS | eBPF Security |
|--------|-------|------|---------------|
| OSI Layer | L3 (Network) | L7 (Application) | L3-L4 (Kernel) |
| Protection Scope | Node-to-node tunnel | Per-service mutual auth | Per-packet filtering |
| Authentication | PSK or X.509 certificates | Client/server certificates | IP-based rules |
| Encryption | AES-128/256, 3DES | TLS 1.2+ (OpenSSL) | N/A (filtering, not encryption) |
| Use Case | Site-to-site VPN, DC mesh | HTTPS FullProxy, zero-trust | DDoS mitigation, access control |
| Performance Impact | Moderate (crypto offload available) | Higher (TLS handshake per connection) | Minimal (kernel fast path) |
| loxilb Implementation | strongSwan integration | sockproxy C layer | TC hook programs |
| Source | `ipsec.go` | `common_mtls.go` | `dpebpf_linux.go` |

4. **"When to Use Each Layer"** decision guide:
   - **IPsec**: When you need transparent L3 encryption between loxilb nodes or to external gateways. Best for: multi-site connectivity, regulatory-mandated encryption in transit.
   - **mTLS**: When you need mutual authentication at the service level with certificate-based identity. Best for: zero-trust architectures, API-to-API security. NOTE: mTLS requires FullProxy mode (mode=4, security=1 or 2). Add `!!! warning` about this constraint per swagger.yml:6360.
   - **eBPF Security**: When you need high-performance packet filtering at kernel level before traffic reaches userspace. Best for: DDoS protection (SYN flood, UDP flood), IP-based access control.

5. **Layered Security Architecture** (Mermaid diagram):
   - Show how all three layers combine:
   - Incoming packet → eBPF TC hook (SYN flood check, IP filter) → IPsec decrypt (if tunnel) → L4 conntrack → mTLS terminate (if FullProxy+HTTPS) → application
   - Show which source files govern each stage

6. **Hardware Acceleration** section (2-3 paragraphs):
   - IPsec supports hardware offload: `hwOffloadEnabled` flag for QAT/DPAA2 crypto accelerators (Source: ipsec.go)
   - Anti-replay protection: `antiReplayEnabled` flag
   - MTU considerations: default MTU 1400 for IPsec tunnels, adjustable

7. **Deep Dive Links**:
   - For detailed IPsec tunnel configuration → [IPsec Configuration](ipsec.md)
   - For mTLS certificate management → [mTLS Configuration](mtls.md)
   - For SYN flood and IP filtering → [SYN Flood Protection](syn-flood.md), [IP Filtering](ip-filtering.md)
